# AI 辅助 UI 设计原则

这份文档把一段关于 AI 做 UI 的实践心得，沉淀成 TinyOffice
后续 Operations Surface 和前端页面整改时要遵守的设计规则。

核心观点很简单：AI 写代码越来越强，但如果没有设计约束，它很容易把
页面越做越乱。

## 为什么需要这份文档

AI 现在已经可以很快做出页面、组件和交互。问题往往不是“能不能做出
来”，而是“随着页面越来越多，整个产品会不会保持一致”。

常见问题包括：

- 信息层级混乱。
- 颜色使用过度。
- 组件风格不统一。
- 每个页面都有自己的间距、边框、按钮、卡片风格。
- 单页看起来勉强能用，但放在一起不像同一个产品。
- 后期不断靠提示词修补，越改越乱。

所以，后续不能只是让 AI “把页面做漂亮一点”。更稳定的方法是：先给
AI 一套设计规则，再让它在规则内实现。

## 总原则

不要让 AI 每次都从零开始猜审美。

每一次比较重要的 UI 工作，都应该先有：

1. 成熟 UI Kit，或者项目内已经确认的本地组件风格。
2. 项目专属的设计系统文档。
3. 关键页面或参考截图。
4. 可复用的布局、按钮、表格、状态标签、面板规则。
5. 浏览器截图验证，包括桌面和窄屏。

## 三种可用方案

### 1. 直接使用成熟 UI Kit

这是成本最低，也最能防止 AI 跑偏的方法。

常见选择包括 shadcn/ui 和其他成熟 UI Kit。

TinyOffice 当前已经正式选择 `shadcn/ui` 作为新前端基座。其他 UI Kit 只保留为历史调研参考或竞品参考，不是当前实现候选，不得在新前端中引入为第二套 UI foundation。

它们的好处是：

- 按钮、表格、表单、弹窗、菜单等组件已经有统一规则。
- 间距、颜色、交互状态比较稳定。
- AI 不需要每次重新发明基础组件。
- 项目不容易积累一堆互相打架的 CSS。

TinyOffice 的 Operations Surface 是内部操作台，不是营销网站。当前实现必须沿用 shadcn/ui 这条克制、清楚、偏后台系统的方向。

### 2. 建立项目自己的设计系统文档

UI Kit 解决的是局部组件一致性，但不能完全解决产品气质、页面结构、
品牌调性和信息层级。

所以项目变大以后，需要一份专属设计系统文档。它可以理解成项目的
设计 DNA。

设计系统文档应该记录：

- 产品气质。
- 使用人群。
- 颜色规范。
- 字体规范。
- 间距规则。
- 页面结构。
- 卡片、面板、表格、按钮、状态标签规则。
- 动效原则。
- 禁止使用的视觉模式。
- 参考产品或截图。

这样后续 AI 做页面时，不是凭感觉生成，而是按同一份规则扩展。

### 3. 设计师与 AI 协作

AI 不会让设计师变得没有价值。相反，设计师更重要的工作会变成“制定
规则”。

比较理想的方式是：

1. 设计师先在 Figma 或关键截图中确定重要页面。
2. AI 从这些页面里提取视觉语言。
3. AI 按同一套规则扩展到列表页、详情页、设置页、仪表盘、营销页。

设计师负责方向，AI 负责执行和扩展。两者不是替代关系，而是协作关系。

## 推荐工作流

以后做重要 UI，可以按这个顺序：

1. 选择 UI Kit 或确认本地设计系统。
2. 创建或更新项目设计系统文档。当前产品样式源是 [TinyOffice UI Style Brief](product/ui-style-brief.md)，旧链接入口是 [TinyOffice Design System](design-system.md)。
3. 先定义一个关键页面。
4. 让 AI 基于关键页面和设计系统文档扩展其它页面。
5. 用浏览器截图检查真实效果。
6. 如果过程中产生了新规则，把规则补回设计系统文档。

TinyOffice 当前优先级：

1. Operations Surface Shell，也就是整体导航和页面骨架。
2. Tasks / WorkRun Detail。
3. Session Explorer。
4. Database。
5. Operating Log。

## TinyOffice Operations Surface 的设计方向

Operations Surface 应该像：

- 本地公司操作台。
- 内部后台工作指挥中心。
- 可以长期使用的办公后台。

Operations Surface 不应该像：

- 营销官网。
- 炫技 Dashboard。
- 每块内容都堆成卡片的演示页面。
- AI 随手生成的通用 SaaS 模板。

优先追求：

- 颜色克制。
- 信息层级清楚。
- 密度适中。
- 状态一眼可见。
- 表格容易扫描。
- 操作按钮明确。
- 页面之间风格统一。
- 空状态、错误状态、加载状态完整。

## 后续 Operations Surface UI 工作规则

开始改 UI 前：

- 先读这份文档。
- 先读 [TinyOffice UI Style Brief](product/ui-style-brief.md) 和 [TinyOffice Design System](design-system.md)。
- 先看现有 shadcn Chat Shell 和后续 Operations Surface 页面结构。
- 判断当前页面属于列表、详情、表格、表单、状态面板还是操作台。

实现时：

- 优先复用 shadcn/ui primitives 和已批准的 TinyOffice 产品组合组件。
- 页面私有 CSS 要尽量少。
- 不要每页重新设计按钮、表格、卡片、状态标签。
- 内部操作台要紧凑、清楚、耐看。
- 重要状态不要只靠颜色表达。
- 危险操作要明显区分，并且需要确认。

完成前：

- 检查桌面宽度。
- 检查窄屏或手机宽度。
- 确认文字不会溢出按钮、表格、面板、侧边栏。
- 代码改动要跑必要检查。
- 如果新增了通用视觉规则，要补进设计文档。

## 禁止事项

- 不要只告诉 AI “做漂亮一点”。
- 不要每个页面自创一套视觉风格。
- 不要在内部操作台里使用大面积渐变、装饰光斑、无意义动效。
- 不要把所有内容都塞进卡片。
- 不要嵌套卡片。
- 不要只用颜色表达状态。
- 不要让重要操作看起来像普通文字。
- 不要为了视觉效果隐藏后台工作、运行时、协作状态。

## 设计系统模板

后续可以用这个模板创建项目级设计系统：

```markdown
# Design System

## 产品气质

这个产品应该给人什么感觉？应该避免什么感觉？

## 使用人群

谁会使用？使用频率多高？是在什么场景下使用？

## 视觉原则

- 原则 1。
- 原则 2。
- 原则 3。

## 颜色

- 背景：
- 面板：
- 边框：
- 主操作：
- 次操作：
- 成功：
- 警告：
- 危险：
- 正文：
- 弱化文字：

## 字体

- 字体族：
- 页面标题：
- 区块标题：
- 正文：
- 元信息：
- 表格：

## 间距

- 页面边距：
- 面板内边距：
- 行间距：
- 列间距：
- 控件高度：

## 布局

- 页面外壳：
- 导航：
- 内容宽度：
- 列表页：
- 详情页：
- 分栏页：
- 空状态：

## 组件

### 按钮

定义主按钮、次按钮、幽灵按钮、图标按钮、危险按钮。

### 面板

定义背景、边框、圆角、内边距、标题样式。

### 表格

定义表头、行高、悬停状态、数字对齐、空状态。

### 表单

定义标签、帮助文字、校验错误、提交区域。

### 状态标签

定义 running、waiting、blocked、completed、failed、disabled 等状态。

## 动效

哪些地方可以动？哪些地方必须稳定不动？

## 可访问性

定义对比度、键盘操作、焦点状态、文字溢出规则。

## 禁止模式

列出这个项目不能使用的视觉模式。

## 参考

链接 Figma、截图、UI Kit、参考网站或参考产品。
```
